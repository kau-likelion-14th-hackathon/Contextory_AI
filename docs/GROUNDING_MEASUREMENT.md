# 근거 판정(Grounding) 실측 기록

> 측정일 2026-08-19 · 대상: 세 파트 저장소의 병합된 PR 30건
> 재현: `python -m scripts.measure_grounding --limit 12 --repeat 3 --json out.json`

## 왜 쟀는가

검색 최고 유사도가 `SIM_THRESHOLD` 미만이면 **LLM을 아예 호출하지 않고** "근거 부족" 화면으로 빠진다.
이 임계값을 감으로 정하면 두 방향 모두 나쁘다.

- 너무 높다 → 멀쩡한 PR도 초안 없이 "사람이 직접 확인하세요"만 나온다
- 너무 낮다 → 무관한 컨텍스트를 근거라고 붙여 잘못된 초안을 만든다

그래서 실제 PR의 점수 분포를 먼저 쟀다.

## 1차 측정 — 임계값 자체는 타당했다

PR 30건(AI 9 / 백엔드 9 / 프론트 12)의 최고 유사도 분포:

| 임계값 | 초안 생성 | 근거 부족 | 빠지는 비율 |
|---:|---:|---:|---:|
| 0.45 | 28 | 2 | 6.7% |
| **0.50** | **26** | **4** | **13.3%** ← 현재 |
| 0.55 | 18 | 12 | 40.0% |
| 0.60 | 9 | 21 | 70.0% |

**임계값을 0.55로 올리면 40%가 초안 없이 빠진다.** 0.5는 유지가 맞다.

## 2차 측정 — 진짜 문제는 임계값이 아니었다

같은 PR을 3회씩 반복 측정하니 **판정이 실행마다 뒤집혔다**.

```
✗ #12  Contextory_AI       0.4954 / 0.5177 / 0.4982
✗ #38  OffCourse_FrontEnd  0.4977 / 0.5798 / 0.4978
```

24건 중 2건(8.3%). 같은 PR을 두 번 분석하면 한 번은 초안이 나오고 한 번은 안 나온다는 뜻이다.
**임계값을 어디로 옮겨도 고쳐지지 않는 종류의 문제다.**

### 원인 — 무작위성이 아니라 쿼리 길이

검색 쿼리는 LLM이 PR 제목·본문을 영문으로 번역해 만든다. 그 번역이 흔들렸다.

```
0.4462  "project domain CRUD API implementation"
0.5458  "... Project entity, ProjectMember entity, ProjectStatus Enum, ProjectPermissionRole Enum ..."
```

기존 프롬프트가 **"concise"** 를 요구해서, 유사도를 만들어내는 기술 식별자를 버리고 있었다.
짧게 요약된 쿼리는 임베딩 검색에서 불리하다 — 즉 결정성만 고정했다면 이 PR은 *항상* 근거 부족으로
빠지는 오탐이 됐을 것이다.

## 조치

| 조치 | 내용 |
|---|---|
| 재현성 | `TRANSLATION_TEMPERATURE=0.0`, `TRANSLATION_SEED=42` (`core/config.py`) |
| 쿼리 품질 | 번역 프롬프트를 "간결하게 요약" → **"식별자를 원문 그대로 남기고 요약하지 말 것"** 으로 변경 |

두 값 모두 `core/config.py` 설정이며 `.env` 로 덮어쓸 수 있다. 코드에 상수를 박지 않았다.

## 조치 후 — 동일 PR 24건 재측정

| 지표 | 이전 | 이후 |
|---|---:|---:|
| 최고 유사도 중앙값 | 0.5585 | **0.6019** (+0.0434) |
| 근거 부족(<0.5) | 4건 | **1건** |
| 실행 간 판정 뒤집힘 | 2건 (8.3%) | **0건 (0%)** |
| 실행 간 변동 폭 중앙값 | 0.0167 | **0.0063** |
| 점수가 오른 PR | — | 18/24 |

저장소별 중앙값도 모두 올랐다: AI 0.6276 / 백엔드 0.6609 / 프론트 0.6022.

## 남은 것

- 여전히 근거 부족으로 빠지는 1건은 프론트 PR이다. 임계값 0.5 기준 4.2%이며,
  저장소 초기 PR처럼 **참조할 과거 컨텍스트가 실제로 없는 경우**가 섞여 있다 — 이건 정상 동작이다.
- `SIM_THRESHOLD` 는 **0.5 유지**를 권한다. 올리면 40%가 빠지고, 내려도 얻는 게 없다
  (0.45로 내려도 추가로 통과하는 건 1건뿐).
- 저장소 코드가 바뀌면 분포도 바뀐다. 재인덱싱 후 이 측정을 다시 돌려 확인할 것.

# 2차 — Confidence 배점 실측 (2026-08-19)

## 발견: 배점 0.2짜리 항목이 구조적으로 항상 0이었다

`STRONG_EVIDENCE_THRESHOLD = 0.75` 로 두었는데, 실제 PR 32건의 검색 결과
**320청크 중 0.75를 넘는 것이 하나도 없었다.**

```
전체 유사도 분포 (n=320)
  p50 0.4727 / p75 0.5688 / p90 0.6127 / p95 0.6440 / p99 0.6694 / 최대 0.7162
```

| 기준값 | 강한 근거로 인정되는 청크 | 강한 근거가 있는 PR |
| ---: | ---: | ---: |
| 0.75 | **0 / 320 (0.0%)** | **0 / 32 (0.0%)** |
| 0.70 | 2 / 320 (0.6%) | 2 / 32 |
| 0.65 | 8 / 320 (2.5%) | 6 / 32 |
| **0.62** | **27 / 320 (8.4%)** | **11 / 32 (34.4%)** |
| 0.60 | 42 / 320 (13.1%) | 15 / 32 |

배점 0.2가 항상 0이면 Confidence 최대값이 0.66 근처로 눌린다. 어떤 PR도 0.8에 닿을 수 없었다.

## 조치 1 — 강한 근거 기준을 관측 분포로 재설정

`0.75 → 0.62` (p90 = 0.6127 바로 위 = 검색 청크 상위 10% 이내).

절대값이 아니라 **분포 기준**이라는 점이 중요하다. 임베딩 모델이나 코퍼스가 바뀌면
`scripts/measure_grounding.py` 로 다시 재고 조정해야 한다.

## 조치 2 — 잔존율을 "쓸 만한 근거를 잃은 비율"로 변경

`filter_ratio` 는 버린 비율 전부를 센다. 그런데 임계값 미달 후보를 버리는 건
필터가 제 일을 한 것이지 손실이 아니다. 검색이 후보를 더 많이 물어올수록
`filter_ratio` 가 올라가 **근거가 좋아졌는데 점수가 깎이는 역전**이 실제로 나왔다.

```
프론트 PR #48 (같은 PR, 같은 코드)
  외부 코드리뷰만 근거    → 0.6107   (filter_ratio 0.0)
  실제 프로젝트 파일 근거  → 0.5800   (filter_ratio 0.4)  ← 근거는 좋아졌는데 점수 하락
```

그래서 `FilterOutcome.information_loss_ratio` 를 도입했다 — **임계값을 넘겼는데도
버려진 것**만 손실로 센다. 임계값 필터에서는 항상 0이고, LLM 필터가 높은 유사도
chunk 를 버렸을 때만 값이 생긴다.

## 결과 — 프론트 PR #48 (동일 PR, 복원 DB)

| | 팀원 머신 (미인덱싱) | 복원 직후 | 두 조치 적용 후 |
| --- | ---: | ---: | ---: |
| confidence | 0.6107 | 0.5800 | **0.8213** |
| 최고 유사도 | 0.6214 | 0.6400 | 0.6426 |
| 강한 근거 | 0건 | 0건 | **4건** |
| 근거 출처 | `cr-*` 외부 코드리뷰 | 실제 `.tsx` 파일 | 실제 `.tsx` 파일 |

## 바닥은 그대로인지 확인

기준을 낮추면 나쁜 분석까지 점수가 올라갈 수 있어 따로 확인했다.

| 사례 | Confidence | 확인 필요 |
| --- | ---: | --- |
| 미인덱싱 저장소 (최고 0.3342) | 0.2671 | O |
| 근거 1건이 겨우 임계값 통과 | 0.4217 | O |
| 외부 코드리뷰만 근거 | 0.6774 | X |
| 프로젝트 코드 근거 (PR #48) | 0.8213 | X |

근거가 없는 쪽은 여전히 낮게 나오고 "확인 필요"가 켜진다.

## 남은 판단거리

- `CONFIDENCE_CONFIRM_THRESHOLD = 0.6` 은 그대로 두었다. 재보정으로 정상 분석이
  0.8대로 올라갔으니 이 기준선도 함께 올릴지는 운영 데이터를 더 모은 뒤 정할 일이다.
- "외부 코드리뷰만 근거"인 경우가 0.6774 로 확인 필요 없이 통과한다.
  프로젝트 코드 근거가 하나도 없는 분석은 별도 신호로 표시하는 편이 나을 수 있다.
