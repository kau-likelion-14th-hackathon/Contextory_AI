# 사람 검토 채점 서식

자동 계산이 불가능한 지표를 채점하는 서식입니다.
`scripts/evaluate_results.py` 는 이 항목들을 `pending_human_review` 로만 표시하고 점수를 만들지 않습니다.

- 검토 대상: `evaluation/results/{프롬프트 변형}/results.jsonl` 의 각 레코드
- 기준: `data/test_samples.json` 의 같은 `id` 샘플의 `expected` 블록과 `reference.review_comment`
- 검토자: (직접 기입)
- 검토일: (직접 기입)

## 1. 한국어 자연스러움 (1~5)

| 점수 | 기준 |
| --- | --- |
| 5 | 한국인 개발자가 쓴 문장과 구분되지 않습니다. 문체가 일관되고 어색한 번역투가 없습니다. |
| 4 | 자연스럽지만 한두 군데 어색한 표현이 있습니다. |
| 3 | 의미는 통하지만 번역투가 눈에 띕니다. 문체가 섞여 있습니다. |
| 2 | 읽는 데 걸림이 있고 직역체가 많습니다. |
| 1 | 의미 파악이 어렵거나 한국어로 보기 어렵습니다. |

감점 사유로 함께 기록합니다: 문체 불일치(`~합니다` 외 사용), 식별자를 한국어로 번역, 원문에 없는 내용 추가.

## 2. 후속 작업 실행 가능성 (1~5)

| 점수 | 기준 |
| --- | --- |
| 5 | 누가 무엇을 해야 하는지 명확하고, 지금 바로 착수할 수 있습니다. |
| 4 | 대체로 실행 가능하지만 대상이나 범위가 일부 모호합니다. |
| 3 | 방향은 맞지만 구체적인 작업으로 옮기려면 추가 해석이 필요합니다. |
| 2 | "테스트를 강화합니다" 처럼 일반론에 가깝습니다. |
| 1 | 이 변경과 무관하거나 이미 PR 안에서 끝난 일을 후속 작업으로 적었습니다. |

## 3. 간결성/명확성 (1~5)

| 점수 | 기준 |
| --- | --- |
| 5 | 불필요한 장황함 없이 핵심이 바로 드러납니다. 같은 내용이 여러 필드에 반복되지 않습니다. |
| 4 | 대체로 간결하지만 한두 군데 중복이나 군더더기가 있습니다. |
| 3 | 읽으면 파악되지만 핵심을 찾는 데 시간이 걸립니다. |
| 2 | 같은 내용이 여러 필드에 반복되거나 서술이 지나치게 깁니다. |
| 1 | 장황해서 무엇이 핵심인지 알기 어렵습니다. |

출력 길이(`Avg Output Chars`)는 참고값일 뿐입니다. 짧다고 높은 점수를 주지 않습니다.

## 4. 변경 요약·목적·전후 설명 정확성

각 필드(`change_summary_ko`, `change_purpose_ko`, `change_reason_ko`, `before_ko`, `after_ko`)마다 판정합니다.

- **정확**: 기준 `expected` 의 해당 항목과 사실 관계가 일치합니다.
- **부분 정확**: 사실 관계는 맞지만 핵심이 빠졌거나 곁가지를 주로 서술합니다.
- **부정확**: diff 나 PR 제목에 없는 내용을 서술했거나 사실이 틀렸습니다.

`change_purpose_ko` 는 PR 본문이 제공되지 않으므로, 근거 없이 목적을 단정하지 않았는지를 함께 봅니다. 비우고 `needs_confirmation` 으로 보냈다면 **정확** 으로 처리합니다. 근거 없이 목적을 단정했으면 **부정확** 으로 처리합니다.

## 5. 역할별 영향 정확성

- **정확**: 영향받는 역할이 기준과 일치하고, 각 역할의 서술이 그 역할이 실제로 할 일을 담고 있습니다.
- **과잉**: 근거 없는 역할을 추가했습니다. 특히 내부 리팩터링에 `design` 이나 `planning` 을 넣은 경우입니다.
- **누락**: 기준에 있는 역할을 빠뜨렸습니다.

역할별 서술이 "확인이 필요합니다" 처럼 어떤 역할에나 붙일 수 있는 문장이면 **과잉** 으로 처리합니다.

## 데이터셋 자체에 대한 검토

프롬프트 결과 채점과 별개로, 기준 데이터셋(`data/test_samples.json`)의 각 샘플도 사람이 승인해야 합니다.
승인 시 해당 샘플의 `human_review.status` 를 `approved` 로 바꾸고 `reviewer`, `reviewed_at` 을 채웁니다.
모든 샘플이 승인되기 전까지 데이터셋의 `status` 는 `candidate_gold` 로 유지합니다.

확인 항목:

1. `source.source_url` 이 실제로 열리고, 그 PR 에 `reference.review_comment` 의 리뷰 댓글이 존재하는가.
2. `input.diff` 가 리뷰 댓글의 지적 대상과 일치하고 민감 정보가 남아 있지 않은가.
3. `expected.issues` 의 각 `evidence` 를 `input.diff` 에서 찾을 수 있는가.
4. `expected` 의 서술이 diff·PR 제목·리뷰 댓글 범위를 넘지 않는가.
5. 확정 카테고리(`classification.category`)가 리뷰 댓글의 실제 내용과 맞는가.
   원래 라벨은 `classification.dataset_comment_type` 에 남아 있습니다.
6. 한국어 문체가 `~합니다` 설명체로 통일되어 있는가.
7. 대조군(`ctx-ctl-*`)이 정말 지적할 것이 없는 코드인가. `issues` 가 빈 배열인가.
